# Brief — Epic 27 «quality window»: spinner + docs freshness + CEM events depth

**Дата:** 2026-10-06 · **Санкция:** выбор мейнтейнера в Q&A по направлению
после закрытия окна v1.8.0 (пункты «Спиннер + docs-freshness» и
«CEM-events углубление»); автономное исполнение, релизный гейт — как всегда
«tag ok».

## Контекст

Очередь §4 v1.8.0 пуста; BENCHMARK Epic 25 оставил два невыполненных
adopt/watch-пункта, batch-confirm v1.8.0 — одно docs-наблюдение. Все три
нити не требуют капчур-материала мейнтейнера и исполняются автономно.

## Состав волны

1. **27.1 tk-spinner** — последний adopt-атом BENCHMARK (finding #3:
   «Spinner absent — progress-bar ≠ indeterminate loader»; паттерны
   taiga loader / polaris Spinner / shoelace spinner / antd spin).
   Заземление = **китовые регистры** (терминал 24T: 0 вхождений спиннера —
   вердикт окна; рулинг-молд 26.1/26.2/26.4: после провала живых
   заземлений атом едет на регистрах кита). Полный цикл FR-16.
2. **27.2 docs-freshness** — наблюдение R3 batch-confirm v1.8.0: проза
   getting-started несёт счётчики эпохи v1/v2 («Девятнадцать
   компонентов», «все 27 компонентов (19 v1 + 8 v2)») при ростере 55
   (45 банк + 10 ТЖ). Свип всех пользовательских доков на фактические
   устаревания счётчиков/состава. Исторические записи (CHANGELOG,
   RELEASE, HANDOFF, спеки) не ретро-правятся.
3. **27.3 CEM events depth** — BENCHMARK finding #10 (watch): events-
   поверхность 0.4/компонент против shoelace 1.9. Механический аудит
   (это окно, фаза A) дал: **все 18 эмиттеров декларированы в CEM —
   механика чиста, разрыв чисто семантический** (у нас меньше событий).
   Потребительские улики: паттерн 24.8 городил DriveFirstAppend-директиву
   из-за отсутствия `page-change` у tk-carousel; tk-toast живёт на
   контроллере без событий жизненного цикла. Фаза A = аудит-отчёт с
   вердиктами add/refuse по правилу «§9 только где потребитель
   упёрся»; фаза B (реализация add-вердиктов) — по объёму, следующими
   окнами, либо хвостом этого.
